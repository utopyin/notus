# Operator round trip

Authorized follow-up to [Slack devbox provisioning](provisioning.md). The user chose a control-plane operator: the loop runs in the Task Durable Object, devbox state is part of the prompt, and devbox-touching tools must ensure the box exists and is awake. This document records the implemented increment and its gates; [product context](../../CONTEXT.md) owns behavior and the [codebase plan](codebase.md) owns ownership.

## Scope

An admitted human input in an `operator` task becomes one invocation with a sequence of persisted steps. Each step is one bounded model round performed outside the object's concurrency gate, using the initiator's saved ChatGPT subscription login through that user's Connection object. The final text becomes the accepted outcome, response and thread answer through the existing outbox. Existing simulation and readiness tasks keep their persisted mode.

The second increment adds one tool, `create_devbox`. The operator knows from its prompt whether a box exists and decides whether the task needs one. A tool call is never executed inline: the model round returns it unresolved, the step becomes a durable wait, control binds provisioning to the operator's own attempt using the environment captured at admission, the existing readiness machinery and callbacks run, and once provisioning settles the tool result is appended to the step and the next round resumes with it. Readiness, wake-up and sleep stay inside the provider path; the tool reports only the settled outcome. No repository, shell or command access exists yet. Follow-up messages in the thread are new turns whose prompt contains the earlier questions and answers.

## Ownership

- `@notus/openai` (tier 1): two explicit backends, the ChatGPT subscription login through the Codex backend and the Platform API key, each with an exact URL, method, content-type and size allowlist; Codex public-client refresh; the neutral `LanguageModel` layer over a caller-supplied `HttpClient`; and the wire shapes a broker exchanges. It never reads storage and never falls back from one backend to the other.
- `accounts/connections` (tier 2): one saved login per canonical user; explicit link, status, revoke and `forward`. Refresh runs within five minutes of expiry, under the host gate, and persists the rotated pair before the new access token is used. Definitive provider answers are recorded by operation ID and replayed without a second provider call; pacing and transport failures are not recorded.
- `executions/steps` (tier 2): sequential steps per invocation with leases, attempts, retry deadlines, encoded response parts, final text, unresolved tool calls while waiting, and failure classification. Bounds: a 150-second lease, six attempts per step, eight steps per turn. `executions/provisioning` additionally captures the environment once per task and can bind to an active operator attempt.
- `entrypoints/operator` (tier 3): the briefing shape, prompt construction, the tool definitions, one model round returning replayable parts and unresolved tool calls, tool-result parts for replay, and the retry classification of model failures.
- `control/operator` (tier 3): schedule invocations and first steps for admitted inputs, claim a step with its briefing, record outcomes, dispatch and resolve waiting tool calls from provisioning status, settle finished or failed turns into accepted outcomes, and compute the next wake including provisioning deadlines. A failed turn still answers, naming the reason, so the answer obligation is never silently dropped.
- `apps/api`: the Connection Durable Object host, the broker `HttpClient` whose only transport is the Connection object, the operator branches of the Task object, and configuration: `NOTUS_MODEL_PROVIDER` selects the backend and defaults to the subscription login, `NOTUS_MODEL` names the model, and `NOTUS_FIXTURE_CHATGPT_OAUTH` or `NOTUS_FIXTURE_OPENAI_API_KEY` seeds the fixture user's connection for the selected backend only.

## Authority and credentials

The initiator recorded in the task reservation selects the connection; later thread participants never change it. Model requests leave the Task object without credentials; the Connection object adds the bearer and account header for exactly one provider endpoint and returns the provider's response. Connection failures reach the model client as ordinary HTTP statuses, so missing, revoked or unrefreshable logins end the turn as authentication failures without a provider call, and rate limits are retried at the provider's hint.

Linking is explicit. The only link path today is the deployment secret for the selected backend: `NOTUS_FIXTURE_CHATGPT_OAUTH`, a login produced by `bun run login:chatgpt`, or `NOTUS_FIXTURE_OPENAI_API_KEY`, a Platform key, placed there by the administrator for the fixture user. The Connection object imports it once, only while unlinked, and remembers the seed fingerprint; revoking blocks the same seed from relinking. API keys do not rotate, so refresh applies only to subscription logins. Tokens are stored in the object's SQLite under Cloudflare storage encryption; application-level envelope encryption and user-driven account linking are later increments.

The Codex public client is not an independently registered application client and the subscription backend is not a documented API. The user accepted running the test under their own ChatGPT account. Confirm the applicable provider terms independently of technical success; never add an API-key fallback.

## Validation

Native workerd checks executed the actual Worker, Task and Connection objects with fake model, token and Slack endpoints: a mention answered by the model text, refresh of an expired seed before the first forward, request headers and stateless body settings, status without token material, per-user object isolation, operation replay without a second call, a follow-up turn carrying thread history, a 429 retried once on the same operation, revocation blocking both forwarding and reseeding while still answering, fulfilled obligations, a quiescent alarm, mode persistence across restart, and zero unexpected outbound requests. The earlier readiness and simulation checks were rerun unchanged. Evidence is machine-local under `/tmp/notus-operator-host/REPORT.md` and `/tmp/notus-regression-host/run1.log`; no repository test files were added.

The test stage was deployed with `NOTUS_MODE=operator` and the fixture login, using `--force` because Alchemy's plan does not detect secret-backed changes. The deployment, Connection class creation, seed import, and live Slack delivery all worked: two mentions produced fulfilled obligations. Both turns failed at the provider, and the answer was the documented fallback. The [live findings](../research/openai-auth.md#live-findings-2026-09-14) record the two blockers: Workers egress to the subscription backend is rejected by a Cloudflare challenge, and the account is refused for Codex use from any origin. The user then chose the Platform API key explicitly for the test stage, accepting API billing, with the subscription path retained in code. The harness covers both backends with fake endpoints. After the stale subscription link was revoked and the key seeded, a live task answered three thread inputs with model-written text and confirmed deliveries; the [intake results](../research/intake-results.md#current-status) record it.

The devbox increment was validated the same way: a mocked model round returning a `create_devbox` call, one inactive Create and one Activate, real enrollment and readiness callbacks against the operator attempt, the tool result replayed as a function-call output in the next request, and the answer delivered; both providers pass 79 checks and the readiness and simulation harness was rerun.
