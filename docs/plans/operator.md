# Operator round trip

Authorized follow-up to [Slack devbox provisioning](provisioning.md). The user chose a control-plane operator: the loop runs in the Task Durable Object, devbox state is part of the prompt, and devbox-touching tools must ensure the box exists and is awake. This document records the implemented increment and its gates; [product context](../../CONTEXT.md) owns behavior and the [codebase plan](codebase.md) owns ownership.

## Scope

An admitted human input in an `operator` task becomes one invocation with a sequence of persisted steps. Each step is one bounded model round performed outside the object's concurrency gate, using the initiator's saved ChatGPT subscription login through that user's Connection object. The final text becomes the accepted outcome, response and thread answer through the existing outbox. Existing simulation and readiness tasks keep their persisted mode.

The second increment adds one tool, `create_devbox`. The operator knows from its prompt whether a box exists and decides whether the task needs one. A tool call is never executed inline: the model round returns it unresolved, the step becomes a durable wait, control binds provisioning to the operator's own attempt using the environment captured at admission, the existing readiness machinery and callbacks run, and once provisioning settles the tool result is appended to the step and the next round resumes with it. Readiness, wake-up and sleep stay inside the provider path; the tool reports only the settled outcome. No repository, shell or command access exists yet. Follow-up messages in the thread are new turns whose prompt contains the earlier questions and answers.

## Ownership

- `@notus/openai` (tier 1): two explicit backends, the ChatGPT subscription login through the Codex backend and the Platform API key, each with an exact URL, method, content-type and size allowlist; Codex public-client refresh; the neutral `LanguageModel` layer over a caller-supplied `HttpClient`; and the wire shapes a broker exchanges. It never reads storage and never falls back from one backend to the other.
- `accounts/connections` (tier 2): one saved login per canonical user; explicit link, status, revoke and `forward`. Refresh runs within five minutes of expiry, under the host gate, and persists the rotated pair before the new access token is used. Definitive provider answers are recorded by operation ID and replayed without a second provider call; pacing and transport failures are not recorded.
- `executions/steps` (tier 2): sequential steps per invocation with leases, attempts, retry deadlines, encoded response parts, final text, unresolved tool calls while waiting, and failure classification. Bounds: a 150-second lease, six attempts per step, and a runaway guard of 200 steps per turn, since product policy imposes no execution cap and the first real editing turn exceeded an earlier guard of eight. `executions/provisioning` additionally captures the environment once per task and can bind to an active operator attempt.
- `entrypoints/operator` (tier 3): the briefing shape, prompt construction, the tool definitions, one model round returning replayable parts and unresolved tool calls, tool-result parts for replay, and the retry classification of model failures.
- `control/operator` (tier 3): schedule invocations and first steps for admitted inputs, claim a step with its briefing, record outcomes, dispatch and resolve waiting tool calls from provisioning status, settle finished or failed turns into accepted outcomes, and compute the next wake including provisioning deadlines. A failed turn still answers, naming the reason, so the answer obligation is never silently dropped.
- `apps/api`: the Connection Durable Object host, the broker `HttpClient` whose only transport is the Connection object, the operator branches of the Task object, and configuration: `NOTUS_MODEL` names the model. The operator always runs on the Platform API with the initiator's key; there is no backend selection, because the subscription backend refuses Cloudflare egress (see below) and so can only serve Codex on the dev box. The fixture seeds (`NOTUS_FIXTURE_CHATGPT_OAUTH`, `NOTUS_FIXTURE_OPENAI_API_KEY`) are gone with the fixture.

## Authority and credentials

The initiator recorded in the task reservation selects the connection; later thread participants never change it. Model requests leave the Task object without credentials; the Connection object adds the bearer for the one Platform API endpoint and returns the provider's response. Connection failures reach the model client as ordinary HTTP statuses, so missing, revoked or unrefreshable logins end the turn as authentication failures without a provider call, and rate limits are retried at the provider's hint.

Linking is explicit. Since 2026-09-15 it happens from the dashboard's account page (see the [dashboard plan](dashboard.md), increment three); before that the only link path was the deployment secret for the selected backend: `NOTUS_FIXTURE_CHATGPT_OAUTH`, a login produced by `bun run login:chatgpt`, or `NOTUS_FIXTURE_OPENAI_API_KEY`, a Platform key, placed there by the administrator for the fixture user. The Connection object imports it once, only while unlinked, and remembers the seed fingerprint; revoking blocks the same seed from relinking. API keys do not rotate, so refresh applies only to subscription logins. Tokens are stored in the object's SQLite under Cloudflare storage encryption; application-level envelope encryption and user-driven account linking are later increments.

The Codex public client is not an independently registered application client and the subscription backend is not a documented API. The user accepted running the test under their own ChatGPT account. Confirm the applicable provider terms independently of technical success. On 2026-09-15 the stage briefly selected the subscription backend for the operator; the first mention failed at the provider with the same edge refusal, and the selection itself was removed rather than restored: the operator runs on the key, Codex on the box runs on the subscription, and nothing falls back from one to the other.

## Commands on the box

The third increment adds `run_command`. A call becomes a durable command bound to the active attempt; the enrolled supervisor long-polls the runtime `poll` endpoint under its epoch-bound readiness credential, claims one command at a time, runs it as the devbox user in `/workspaces` with a fixed environment that excludes every callback credential, and reports the bounded result through `observe`. A poll from a newer epoch fails commands an older runtime still held; nothing is re-run automatically. If the box has not polled recently the dispatch asks for a wake through the existing provisioning path. Commands without a dev box, on a blocked box, or without a runtime report within the command timeout plus ten minutes fail with an explanation the model sees. Output is truncated at 64 KiB per stream and a command runs at most two minutes.

A held poll keeps the Task object busy, so the supervisor only long-polls while work is flowing: for three minutes after readiness and after every command result it polls with a 20 second wait and no gap; once that window passes it switches to instant checks spaced 5 seconds apart, doubling to a 45 second cap. The cap stays under control's 60 second stale threshold, so a command queued for an idle box is picked up within a minute without a provider wake, and the first result restores continuous polling. A box that Namespace stopped as idle is a separate matter: its supervisor restarts on wake and polls immediately. The backoff shipped as image version 9.

Offline validation: the harness drives the poll, claim, second-poll, wrong-credential, observe, identical replay and conflicting replay cases and checks the output replays into the next model round, 97 checks across both providers; the readiness and simulation harness was rerun. The real executor was run inside the new Linux AMD64 image with exit codes, cwd, UID, filtered environment, timeout kill and truncation checks. The image was published as version 2 of the same repository, audited with the previous policy (the registry dropped the `shell` field this time, which the audit now tolerates), and the workspace environment moved to revision 2; evidence is machine-local under `/tmp/notus-commands-publish/` and `/tmp/notus-environment-commands/`. Tasks that captured revision 1 keep their existing boxes; new tasks use the new image. The first live task on the new image ran the full chain in eleven seconds from Create to observed command result; the [intake results](../research/intake-results.md#current-status) record it.

## Specialist rounds

The fourth increment adds `run_specialist`. One call is one round: a named Codex agent in a Herdr pane on the box, working in the repository checkout, receives the operator's instructions and writes a Markdown report the round returns. The same name reuses the same live agent, so a later round keeps its memory; a new name starts another agent. The round is an ordinary runtime command with a 45 minute budget: the supervisor creates the Herdr workspace on first use, starts `codex` with approvals and its sandbox bypassed (the box is the sandbox), submits the prompt with a wait for `idle` or `done`, and prints the report file the agent was told to write. A round that settles without a report fails with the agent's recent screen in stderr, so the operator sees why. The agent edits files but cannot publish: `push_branch` remains the only way out, and the prompt tells the operator to check the diff first.

Since 2026-09-16 the round's instructions are composed by control from the workspace's instructions captured when the task started (see the [dashboard plan](dashboard.md), increment five): the named role's Markdown, then the operator's own instructions, each under its own heading. The briefing lists the roles with their first line; naming a role the workspace never defined fails the call with the list, without a runtime command.

Two things keep a round alive and signed in:

- **Idle markers.** Namespace measures activity by connections and sessions, not load, so a box working unattended would be stopped as idle. Every runtime command calls the template's busy hook, `/usr/local/libexec/notus/busy start|end <command id>`, around its run. The Namespace template's hook creates a file under `/.namespace/tasks` for the command's duration, following Namespace's long-running-tasks guide. A template without the hook has nothing to signal; a failing hook only logs a warning. The [compute plan](compute.md#box-side) owns the hook.
- **Agent login.** Codex on the box uses the initiator's ChatGPT subscription, never the operator's model connection and never an API key. Each user has a second Connection object, `agent:<user>`, seeded from `NOTUS_FIXTURE_AGENT_LOGIN` for the fixture user; it holds the refresh token and rotates it like the operator connection. When the runtime claims a specialist command, the Task host asks that object for a login that outlives the round: the access token is refreshed first if it would expire within the round's budget plus ten minutes, because the box cannot refresh. The reply carries a Codex `auth.json` with the access and OpenID tokens, the account ID and an empty refresh token; it is written to `~/.codex/auth.json` by the round's shell, never persisted by control, and never appears in a task snapshot. The OpenID token is now captured by `bun run login:chatgpt` and by every refresh, and stored beside the pair.

The image gains the pinned Codex CLI and `jq`. Version 7 shipped only the `codex` binary, and the first live round showed why that is not enough: Codex 0.154 routes its execution tool through a separate `codex-code-mode-host` helper, so every command the agent tried failed with that binary missing, the agent reported it could not work, and no report was written; the operator then made the README change itself and opened [pull request #3](https://github.com/<owner>/<repo>/pull/3). Version 8 installs `codex`, the code-mode host and `rg` from the release package archive. Codex is configured per round to trust the checkout and skip update prompts, so it never stops at a startup dialog.

Offline validation: the harness drives a `run_specialist` call through the actual Worker and Task object: the polled command carries the checkout path, agent name and budget; the one-round login file holds the refreshed access and ID tokens, the agent account and an empty refresh token, and never the operator connection or any refresh token; the refresh happened with the agent connection's own token because the login would have expired during the round; the report replays into the next model round; the answer is delivered; and the agent connection reports linked status without secrets. 151 checks across both providers; the readiness and simulation harness passes 41.
