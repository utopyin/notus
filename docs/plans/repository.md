# Repository access

Authorized follow-up to the [operator plan](operator.md). The user chose the private repository `<owner>/<repo>` as the first target and a dedicated GitHub App as the authority. This document records the implemented increment and its gates; [product context](../../CONTEXT.md) owns behavior and the [codebase plan](codebase.md) owns ownership.

## Scope

The operator can check the task's repository out on its dev box, run commands inside it, push its changes to a branch under the initiator's GitHub login, and open a pull request into the default branch. The App now holds Contents write and Pull requests write, but no single Notus token ever does: each operation mints its own token with the least permission it needs. PR feedback as a task source is the next increment.

## Tools and control

- `push_branch { slug, message }`: the supervisor commits the whole checkout as `Notus <notus[bot]@users.noreply.github.com>` and pushes `HEAD` to `<initiator login>/<slug>`. The login is the initiator's GitHub login from their sign-in profile (`notus` when they have none), captured with the repositories at admission; control validates the slug, derives the branch, and refuses the default branch, and the executor pushes an explicit refspec to that branch only. The Contents-write token exists in that one git process's environment. An empty diff is refused rather than committed.
- `create_pull_request { slug, title, body }`: runs in the control plane as a leased action from the Task alarm, never on the box, with a token carrying Pull requests write, Contents read and Metadata read. Contents read is required: GitHub reads both branches when opening a pull request, and the first live attempts with Pull requests write alone failed with 422 `not all refs are readable`. The token never carries Contents write, and the provider package refuses to mint that combination. Returns number and URL; a rejection now carries GitHub's short validation message to the model. After the fix, a follow-up in the same Slack thread opened [<owner>/<repo>#1](https://github.com/<owner>/<repo>/pull/1) from `utopyin/polish-readme-documentation` into `main`, authored by the App's bot identity: the first complete run from a Slack mention to a pull request that only a human can merge.
- `checkout_repository { repository?, pullRequest? }`: since 2026-09-15 a checkout lands on the default branch or, given a pull request number, on that pull request's head branch, and reports the default branch separately so a later pull request keeps the right base. The box resolves the head branch itself with the read token it already holds: the branch at the same commit as `refs/pull/<n>/head`, restricted to branches of this repository, so a fork's pull request has no continuation. A repeat checkout on the same box switches branches only when asked for a different one, so local commits survive. Continuing a pull request is then `checkout_repository` with its number, the change, and `push_branch` with the slug of its branch, which stays under the initiator's login policy. Image v11 carries the runtime side; older runtimes report no default branch and control falls back to where they landed.
- `run_command` still runs without credentials, so `git push` from bash always fails; bash on the box cannot authenticate to GitHub at all.
- No merge exists anywhere: there is no merge tool, the merge endpoint requires Contents write and Pull requests write on one token and Notus never mints both together, and the push refspec can never target the default branch. This repository cannot carry branch protection on its current plan, so these application rules stand alone; a human with write access merges through GitHub.

## Ownership

- `@notus/github` (tier 1): App JWT signing with WebCrypto from a PKCS#8 key, and one operation: a repository-scoped installation token with read-only permissions. Failures carry status and classification only.
- `executions`: the repository captured once per task at admission, a `checkout` command kind beside `shell`, a working-directory allowlist of `/workspaces` or one checkout under it, and the checkout result on the command observation.
- `entrypoints/operator`: the `checkout_repository` tool, a `cwd` parameter on `run_command`, and the repository line in the prompt including the checkout path once one exists.
- `control/operator`: dispatch and evaluation for checkout calls, including immediate failures when no box, no repository or no App exists.
- `apps/api`: `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY` are the App; a task's repositories are the ones its workspace covers through a GitHub installation connected from the dashboard, and every token is minted through the repository's own installation. There is no fixture: a stage is deployed, signed into, and connected the same way whether it is a developer's or production. The Task object mints the token only when the enrolled supervisor claims a checkout command, outside its gate, and returns it once in that poll reply. Without an App the claimed command fails closed and the runtime receives nothing.
- `apps/devbox`: the checkout executor runs `git clone` of the default branch, shallow and single-branch, and the push executor commits and pushes to the task branch; both receive their token through git's environment configuration for that process only. It never appears on a command line, in `.git/config`, or in the supervisor's own environment. A repeated checkout reports the existing checkout.

## Limits

Repository commands run as the same OS user as the supervisor. A hostile build script could read the runtime's callback journal, whose credential grants only this attempt's runtime authority, or the git objects of the checkout. This is a documented limit for the disposable test scope, not isolation. The [codebase plan](codebase.md#runtime-and-data-ownership) keeps enforced isolation as a gate before any untrusted repository.

Later fetches need a fresh token; only the initial clone is covered. Tokens expire after one hour and are not cached.

## Validation

Harness: 111 checks across both model providers, including the App JWT and read-only scope of the token request, the credential appearing only in the poll reply and never in the task snapshot, the checkout result replayed into the next model round, the prompt reporting the checkout path, a command in the checkout directory, and the fail-closed path without an App. The readiness and simulation harness was rerun. The clone executor ran inside the version 3 image against a local repository: first clone, idempotent repeat, no token in git configuration, and a missing branch failing with exit 128. The App files were verified by minting one scoped token from the workstation. Image version 3 was published and audited, the workspace environment moved to revision 3, and the test stage was deployed with the App secrets. Live: a new task created devbox `l879m39ao36u2`, checked out `<owner>/<repo>` at `main` and answered with HEAD `0fb4c3afbc52c5b8d2bf25c87dc1a4475644bb4a`, which matched the repository's current `main` on GitHub at that moment; the [intake results](../research/intake-results.md#current-status) record it.

Idle supervisors keep long-polling every twenty seconds; backing off while idle is a small follow-up.

A live lesson: the first push attempt stranded a box. The branch naming policy had changed to `<initiator login>/<slug>` after image version 4 was published, and the shared wire schema on that box still rejected anything outside `notus/`, so decoding the poll reply failed permanently and the supervisor exited with the command left claimed. The wire schema now accepts any safe git ref and the naming policy lives only where control builds the command, published as image version 5 with environment revision 5. Boxes on older images cannot be upgraded in place; the stranded task's push fails by deadline with an explanation, and new tasks use the new image.

A second live push, on image version 5, failed in 110 ms with GitHub's "Repository not found" while the checkout in the same task had succeeded. That message on a private repository means GitHub accepted a credential but would not map it to the repository: no token, an invalid token or a malformed token produce git's username prompt instead, and a valid read token produces 403. Each link was then tested in isolation and passed. A Worker-minted push token, obtained through a temporary binding-only probe, carried Contents write and Metadata read on `www` and received HTTP 200 on git's first push request from Cloudflare's network. The same executor pushed successfully inside the image. A known-good token pushed successfully from the live box itself, whose git configuration held no helper or header. The failure did not reproduce and its cause is not established. Every minted token now logs the permissions and repositories GitHub granted, so a recurrence records what the box received. Namespace also writes the account owner's git identity into the box's global configuration; commits made through `push_branch` override it with the Notus identity, but commits made from `run_command` would not.

The trace exposed a real defect that turned the one-off failure into a dead end. After a failed push the commit already existed locally, so a second `push_branch` call found nothing to commit and exited before pushing. The executor now commits only staged changes and pushes whenever HEAD differs from the remote default branch, refusing only when there is nothing to publish. An in-image test covered a refused empty push, a failed push that keeps its commit, a no-change retry that publishes it, and an idempotent repeat. This shipped as image version 6 with environment revision 6.

The push and pull-request increment was validated offline the same way: 121 harness checks across both providers cover the push command with a Contents-write token that carries no Pull requests write, the pull request opened by control with a Pull-requests-write token that carries no Contents write, both results replayed into the next round, and the pull request never becoming a runtime command; the push executor ran inside the version 4 image against a local bare repository, refusing an empty diff, landing a bot-authored commit on a task branch while `main` stayed untouched, and rejecting a pull-request command on the box. Image version 4 was published and audited, the workspace environment moved to revision 4, and the App's installation grants were verified by minting a write-scoped token. The App is installed on all repositories of the account; Notus only ever scopes tokens to the configured one.

## Pull request feedback

Comments on a task's pull request continue that task. The GitHub App delivers `issue_comment`, `pull_request_review` and `pull_request_review_comment` events to `/github/events`, and the Worker verifies each delivery's `X-Hub-Signature-256` against `GITHUB_WEBHOOK_SECRET` before reading it.

- **Scope.** Only deliveries for the configured installation and repository are considered; the repository is seeded as an allowed source beside the Slack channel.
- **Authority.** A comment counts only when its author holds admin, maintain or write on the repository, checked with a Metadata-read token. Other comments are acknowledged and ignored. Comments from bots or any app are ignored before the role check, so Notus cannot answer itself.
- **Routing.** `create_pull_request` appends a hidden `notus:task` marker to the body. The marker is only a hint: on the first comment for an unrouted pull request, the Worker asks the marked Task object to confirm, and the task confirms only if it holds a completed pull-request action for that number in its own repository. Only then are the attached source and the D1 route recorded. Editing the marker cannot route feedback into another task, and a comment before the pull request existed is kept as context.
- **Task state.** The pull request becomes an attached source that receives inputs and replies but never takes updates; the Slack thread stays the only update channel. Admission from an attached source requires the task's own initiator and workspace, so feedback never changes the owner. Routes are no longer unique per task, since one task now owns two conversations.
- **Answers.** Each accepted comment is an input with an answer obligation and a GitHub eyes reaction as receipt. The operator sees it labeled as pull request feedback. Its answer is posted as a pull request comment, or as a threaded reply for review comments; reviews themselves cannot carry reactions. Discussion tokens carry Pull requests write and Contents read, never Contents write.

Validation: the harness drives signed deliveries through the actual Worker, inbox and Task object, covering a bad signature, a ping, a bot comment, a non-writer, a forged marker for an unopened pull request, a writer comment that attaches once, an identical redelivery, a review comment answered in its thread, both eyes reactions, no Slack post for GitHub answers, and the discussion token scope. 143 checks pass across both model providers, and the readiness and simulation harness was rerun. Limits: GitHub does not retry failed deliveries, so a 503 during an outage loses that comment; a comment arriving in the instant between opening the pull request and recording its result is not attached; unauthorized comments are not kept as review context yet.

Live result on 2026-09-14: pull request #2 on `<owner>/<repo>` was opened with the marker. A writer review comment asking to rephrase routed to that task, the operator pushed a second commit to the same branch, and the bot replied in the review thread; its own reply was ignored as a bot comment. The comment posted before the App subscribed to events was never delivered and cannot be redelivered. The App currently subscribes only to `pull_request_review_comment`; top-level comments and reviews need `issue_comment` and `pull_request_review` ticked.
