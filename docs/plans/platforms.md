# Platforms plan

A source is where humans and Notus talk: a Slack thread, a pull request conversation. Today the [contract](../../packages/contracts/src/source.ts) is neutral but everything around it is not. `workspace_channels` stores Slack team and channel IDs and smuggles GitHub repositories through the same columns; ingress accepts one Slack channel and one GitHub installation named in the Worker's environment rather than what a workspace configured; the tasks `Sources` service is one object with `if (kind === "github")` inside; and the dashboard has a "Slack channels" page because that is the only shape the backend offers.

This plan turns the source into a contract with registered implementations, the way `@inbox/platform` describes messaging networks: one vocabulary package that names the platforms, what a platform can do, how it is presented and how it is connected; a domain whose modules implement that vocabulary for one platform each over the provider SDKs; a registry the hosts yield to reach an adapter without ever branching on its name. The tiers are the codebase plan's. A package knows nothing of Notus: `@notus/platform` is the contract and its entities, `@notus/slack` and `@notus/github` are SDKs. A domain is where product decisions live: `@notus/platforms` is the neutral domain (the registry, and in increment two installations and scopes), `@notus/platform-slack` and `@notus/platform-github` each implement the contract over one SDK and are the only importers of it. Entrypoints compose against `@notus/platforms` alone; the app provides the registry with the adapters it deploys. "Platform" rather than "source" because the seam runs both ways: input arrives through it and answers leave through it. Core code that pulls a platform identifier apart has reached past the seam.

## Vocabulary: `@notus/platform`

Replaces `@notus/contracts/source`. Depends on `effect` only, so the dashboard imports descriptors without pulling a provider client.

| Module            | Owns                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `platform.ts`     | `Platform = Schema.Literals(["slack", "github"])`. The single definition every enum, column and client derives from. Append-only.                                                                                                                                                                                                                                                     |
| `ids.ts`          | Branded opaque strings: `InstallationId` (a Slack team, a GitHub App installation), `PlatformId` (a channel, a repository, a thread, a message, a comment). Only the owning adapter parses or builds one. `InstallationRef { id, platform, installationId }` is what adapters receive.                                                                                                |
| `capabilities.ts` | `Capability` literals and `Capabilities.ensure`: `input:start`, `input:message`, `input:review`, `output:update`, `output:reply`, `output:react`, `scope:list`, `conversation:open`. An operation an adapter cannot perform fails `CapabilityNotSupportedError` before any I/O. Attachment flags (`receive`, `reply`, `updates`, `reaction`) narrow these per attachment.             |
| `descriptor.ts`   | `PlatformDescriptor`: pure data and pure functions. Name, icon key, accent, the scope noun ("channel", "repository"), `scopeLabel`, `conversationUrl`, the baseline `Capabilities`, and `install`: how a workspace connects an installation (`{ kind: "oauth" \| "app-install", url(state) }`). `PLATFORM_DESCRIPTORS` is total over `Platform`, so a missing one is a compile error. |
| `source.ts`       | `Source { platform, installationId, scope: PlatformId, conversation: PlatformId }`, `ReplyTarget { source, target: PlatformId }`, `Actor { platform, installationId, externalId }`, `Input`, `Reservation`. `scope` becomes explicit so authorization is a lookup, never a parse.                                                                                                     |
| `ingress.ts`      | `PlatformIngress { verify(request), normalize(installation, payload) → Normalized }` where `Normalized` is `{ type: "input", input } \| { type: "acknowledge", body } \| { type: "ignored" }`. Slack's URL challenge is an acknowledgement, not a special case in the host.                                                                                                           |
| `adapter.ts`      | `PlatformAdapter { platform, descriptor, ingress, forInstallation(ref) → InstallationSurfaces }` with `InstallationSurfaces { scopes: Scopes, conversations: Conversations, identity: Identity }`: list scopes the app can see; resolve reply and update handles for a target; describe an actor. Every handle is runtime-only; only `ReplyTarget` is persisted.                      |
| `errors.ts`       | `PlatformNotRegisteredError`, `DuplicatePlatformRegistrationError`, `InstallationNotFound`, `CapabilityNotSupportedError`, `IngressError`, `DeliveryError` with the existing `rate-limited \| rejected \| ambiguous` classification and `retryAfter`.                                                                                                                                 |
| `conformance/`    | One case list every adapter runs against its own fixtures: an unsupported capability fails before I/O; `normalize` ignores the app's own messages; a reply target round-trips through the registry; `scopes.list` returns only scopes the installation can act in; a throttled delivery carries `retryAfter`. Adding a case turns every adapter red at once.                          |

Platform-specific data that the neutral half cannot hold lives in a tagged pocket per platform (`SourcePlatformData`), never in extra columns: a Slack conversation carries `{ _tag: "slack", threadTs }`, a GitHub one `{ _tag: "github", number }`. A field moves into the neutral half when a second platform needs an equivalent.

## Domains: `@notus/platforms`, `@notus/platform-slack`, `@notus/platform-github`

`@notus/platforms/registry` is `Platforms.Service { forPlatform(platform) → PlatformScope, forInstallation(ref) → InstallationPort }`, built from `Platforms.layer(Effect.all([slack, github]))`; duplicate registration and an unregistered platform are typed failures and the raw adapter never escapes. `@notus/slack` and `@notus/github` stay SDKs (`service.ts`, `app.ts`, `webhooks.ts`: clients, verification, decoding), with nothing about Notus in them. `@notus/platform-slack/adapter` and `@notus/platform-github/adapter` each assemble a `PlatformAdapter` from their SDK: what counts as start intent, how a review comment is phrased for the operator, which marker claims a task, who may steer a pull request. The tasks domain's `sources.ts` and the control inbox's GitHub normalization move into those adapters; what remains in tasks is the neutral attachment and delivery logic, which asks `Platforms.forInstallation` for handles. The rule is the one the codebase plan already states: the provider package verifies and decodes, the adapter normalizes, the shared use case resolves identity and authorizes.

## Data

Two workspace-owned tables replace `workspace_channels`:

- `workspace_installations (key, workspaceId, platform, installationId, label, installedBy, installedAt)`, keyed on `(platform, installationId)`: an installation belongs to one workspace, the one whose administrator last completed the platform's consent; installing it elsewhere moves it and drops the previous holder's scopes through it.
- `workspace_scopes (key, workspaceId, platform, installationId, scope, label)`: the channels and repositories a workspace listens in and works on.

`Access.workspaceOf(ref)` names the workspace an installation belongs to and `Access.authorizeSource` is one lookup on `(workspace, platform, installation, scope)`. Ingress resolves the workspace from `(platform, installationId)` before normalizing and refuses uncovered scopes before asking the adapter about the actor, so no provider call is spent on a repository nobody enabled. The Worker's `SLACK_TEAM_ID`, `SLACK_CHANNEL_ID` and `GITHUB_APP_INSTALLATION_ID` stop being routing configuration; the dev stage keeps them as fixture seeds that insert one installation and one source per platform. The adapters still accept only the configured installation until the install flows of increment three store a token per installation.

## Installing

Connecting a platform is the same two steps for every platform, split the way `@inbox/platform` splits linking: the adapter's `installing.begin(intent)` says where to send the administrator and `installing.complete(intent, query)` turns the platform's redirect into an `Installed { installationId, label, credential }`; the workspace decides whether the administrator may install, keeps the intent and records the result. The intent is a single-use, fifteen-minute row in `workspace_install_intents`, keyed by the nonce the platform carries back as `state`, so no signing secret is needed. The platform returns to `https://api.<stage>.notus.run/platforms/<platform>/install`, the API's own route (`apiOriginOf` in `@notus/shared/hosts` derives it from the dashboard origin). The session cookie lives on the dashboard's origin, so that route only bounces the request to the same path there; the dashboard forwards it with the cookie to `dashboardCompleteInstall`, which consumes the intent, refuses anyone but the user who began it, completes the install and lands on the dashboard's Platforms page with `?installed=<platform>` or `?install=<reason>`. An installation belongs to one workspace: installing one another workspace holds fails with `installed-elsewhere` until that workspace uninstalls it.

- **Slack** is OAuth v2 with the app's client: `begin` builds the authorize URL with the bot scopes (`app_mentions:read`, `channels:history`, `channels:read`, `chat:write`, `groups:history`, `groups:read`, `reactions:write`); `complete` exchanges the code at `oauth.v2.access` and yields the team and its bot token and bot user.
- **GitHub** installs from the App's own page (`https://github.com/apps/<slug>/installations/new`) and returns to the App's setup URL with `installation_id`; `complete` confirms the installation through the App JWT and takes the account it belongs to as the label. No credential: the App key is deployment configuration and mints installation tokens as before.

**Credentials** are the adapter's own JSON on the installation row (`workspace_installations.credential`), behind the contract's `InstallationCredentials { get, put }` which `@notus/workspaces/credentials` implements. Only the API and Task Workers read it; no projection carries it. Adapters resolve every installation through it: the Slack adapter builds a client per team from the stored bot token and recognizes its own bot user from the same record, the GitHub adapter binds the App to `ref.installationId`. Nothing is pinned to the deployment's team or App installation any more; the fixture is an ordinary seeded installation whose credential comes from the same environment variables as before.

## Dashboard

One **Platforms** page replaces Channels: a section per installation, headed by the descriptor's name and icon and the installation's label (the team, the account), listing the scopes the workspace covers with a picker filled by `dashboardListScopes` for that installation and a manual identifier form where the platform lists nothing; a disconnect action per installation; and, for each installable platform the workspace has not connected, one button (`dashboardInstallUrl`) that sends the administrator away. The page branches on descriptor fields (`name`, `icon`, `scopeNoun`) the API projects, never on the platform.

## Boundaries that do not move

- The registry hands out scopes and ports, never adapters; hosts cannot reach a provider client through it.
- Authorization stays in workspaces and control: an adapter answers platform questions and owns platform resources, it never decides whether a workspace may act.
- Provider secrets stay on the API Worker; the dashboard receives descriptors and status projections.
- Persist `ReplyTarget`, never handles.

## Increments

1. **Contract and registry.** `@notus/platform`, `@notus/platforms`, the two adapter domains wrapping today's code, `Platforms` provided by the API and Task hosts, tasks and control consuming it. Same tables, same fixture, no behaviour change; the offline harness passes unchanged.
2. **Installations and scopes.** The two tables, `Access` on `(installation, scope)`, ingress routed by installation, fixture seeding through the same path, environment variables reduced to seeds.
3. **Installing.** Install intents and callbacks, per-installation credentials behind the contract's store, adapters resolving any installation, the Platforms page. Supersedes dashboard increment four's installation flow.
4. **Conformance.** The shared case list and each adapter's fixtures in the offline harness.

- **Increment one shipped on 2026-09-15.** `@notus/platform` holds the vocabulary (`Platform`, branded `InstallationId`/`PlatformId`, `Source` with an explicit `scope`, `Capabilities`, `PlatformDescriptor` with a total `PLATFORM_DESCRIPTORS`, `PlatformIngress`, `PlatformAdapter` and the errors); `@notus/platforms/registry` is the `Platforms` service; `@notus/platform-slack` and `@notus/platform-github` implement the contract over the SDK packages; `apps/api/src/platforms.ts` builds one registry for both hosts and `apps/api/src/ingress.ts` is the single `/<platform>/events` route: the adapter verifies and normalizes, the route resolves the workspace, asks the adapter's `identity.mayParticipate`, attaches a conversation its task confirms it opened, and admits. The control inbox derives keys from `(platform, installation, scope, conversation, target)` uniformly and checks `input:start` against the descriptor; `Access.authorizeSource` is one lookup on `(installation, scope)`; an opened pull request records its `Source`, so attachment is an equality check. `workspace_channels`, the fixture and the environment variables are unchanged, as planned. Not in the contract yet: the descriptor's `install` action and the conformance suite.
- **Increment two shipped on 2026-09-15.** `workspace_installations` and `workspace_scopes` (migration `20260915091203_platform_installations`, dropping `workspace_channels`); `Access.workspaceOf` and a scope-keyed `authorizeSource`; the inbox exposes `workspaceOf` and `covers`, and the ingress route resolves the workspace from the installation table and drops uncovered scopes before the adapter's actor check. `Workspaces.addScope`/`removeScope` require the installation to be the workspace's own. The dashboard's channels page reads the workspace's Slack installation and lists its scopes through `dashboardListScopes(workspaceId, platform, installationId)`; the API projects installations, sources and scopes as plain strings so no brand crosses the RPC. The fixture seeds one installation and one source per platform from the same environment variables as before.
- **Increment three shipped on 2026-09-15.** `@notus/platform/installing` and `@notus/platform/credentials`; `PlatformAdapter.installing`; `@notus/slack/oauth` and a per-token `Slack.make`; the GitHub App bound per installation (`App.forInstallation`, `App.installation`); `workspace_install_intents` and the `credential` column (migration `20260915092145_installation_credentials`); `Workspaces.beginInstall/takeInstallIntent/install/uninstall`; the `/platforms/<platform>/install` route and `dashboardInstallUrl`/`dashboardUninstall`; the Task host reads the shared database for credentials; the Platforms page. Needs, per deployment: `GITHUB_APP_SLUG`, the Slack app's redirect URL and bot scopes, and the GitHub App's setup URL pointing at the install route. Not yet: the conformance suite; encryption of credentials beyond the platform's own; repository listing for GitHub installations (the descriptor withholds `scope:list`, so the page offers the manual form).
- **Naming settled on 2026-09-15.** The dashboard page is **Platforms** (`/<slug>/platforms`) and the covered places are **scopes** (`workspace_scopes`, `Workspaces.addScope/removeScope`, `dashboardAddScope/RemoveScope`, `view.scopes`; migration `20260915093131_workspace_scopes` renames the table). "Source" keeps its product meaning: a conversation attached to a task.
- **The fixture is closed for execution (2026-09-15).** A task's repositories are the GitHub scopes its workspace covers, captured as candidates at admission (`execution_repository.candidates`, migration `20260915132455_repository_candidates`) with each one's installation; the only candidate is chosen outright, otherwise the operator names one in `checkout_repository` and the choice is final. Tokens and pull requests go through that installation. The default branch is whatever the clone lands on (the checkout reports it; pushes compare against `origin/HEAD` and pull requests take it as base), so nothing configures it. Branches live under the initiator's GitHub login, kept on the user profile from sign-in (`account_users.githubLogin`, migration `20260915132456_github_login`; users who linked GitHub before this re-link once), `notus` when there is none.
- **The workspace fixture is gone (2026-09-15).** No stage seeds a workspace, an identity, an installation or a scope any more: every stage is deployed, signed into and connected from the dashboard the same way. `NOTUS_WORKSPACE_ID`, `NOTUS_FIXTURE_SLACK_USER_ID`, `NOTUS_FIXTURE_REPOSITORY`, `NOTUS_FIXTURE_GITHUB_LOGIN`, `SLACK_TEAM_ID`, `SLACK_CHANNEL_ID`, `SLACK_BOT_TOKEN`, `SLACK_BOT_USER_ID` and `GITHUB_APP_INSTALLATION_ID` are no longer read; the Slack app is `SLACK_SIGNING_SECRET` plus its OAuth client, the GitHub App is `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY` and `GITHUB_APP_SLUG`. The offline harness seeds its workspace, identity, installations and scopes straight into D1. What remains seeded is the model connection (`NOTUS_FIXTURE_USER_ID` with `NOTUS_FIXTURE_AGENT_LOGIN` / `NOTUS_FIXTURE_OPENAI_API_KEY` / `NOTUS_FIXTURE_CHATGPT_OAUTH`), until the dashboard's Connections increment replaces it.
